# Демонстрация для жюри

Откройте `review.html` из завершённого комплекта BCC. В паспорте покажите Git SHA, имя модели, отпечаток входа и исход сверки. По SHA откройте на GitHub тот же код. Команда сборки версии 0.6.3 приведена в README.

**1 минута — решение аналитика.** Откройте карточку календарного примера. Прочитайте дату покупки, дату проведения и ожидаемый счётчик. Сопоставьте с правилом выбора месяца. Владелец продукта должен решить, какой месяц верен. После согласования QA сможет однозначно проверить пограничный случай.

В исходнике BCC покупка на 4 000 ₸ совершена 31 января в 23:58, проведение произошло 1 февраля в 00:03. Спросите, какой месячный счётчик должен вырасти. Попросите QA записать два разных ожидания для тех же событий. Покажите, почему приёмку этого сценария стоит отложить до решения владельца. Сумма покупки здесь служит входом теста. Экономический эффект пилота требует отдельного измерения.

**1 минута — устройство проверки.** Покажите обе цитаты и координаты. Gemini извлекает смысловые замечания, правила связывают условие с примером. Для прогона с флагом `--verify` откройте массив verification в JSON и покажите решение по конкретной цитате.

**30 секунд — почему PDF.** По условию на вход подаётся PDF. Обычное извлечение текста рвёт предложения, разбивает таблицы на отдельные ячейки и теряет заголовки. В версии 0.6.1 правила без модели находили на PDF-версии документа BCC 0 замечаний, а на Markdown-версии того же документа — 5. Версия 0.6.2 восстанавливает заголовки по шрифту, таблицы по линиям сетки и абзацы по межстрочным интервалам. PDF с таблицами в рамках даёт ту же карту требований, что и Markdown. Правила контракта и единиц без модели находят 13 замечаний: статусы 201 и 404 без описания, раздел 403 со ссылкой на 404, ошибку под статусом 200, разные типы `amount` и `enabled`, тиыны и тенге без правила пересчёта. Покажите любую из этих карточек и строку-источник.

**1 минута — решение владельца и повторная проверка.** Покажите исходный конфликт на примере квитанции. Через 24 часа требование RC-1 обязывает хранить её ещё 48 часов, а RC-2 задаёт максимум сутки. В учебном сценарии владелец согласовал сутки. Команда воспроизводит изменение и выводит проверочное значение для QA. [Отчёт, сформированный CLI](EXAMPLE_COMPARISON.md).

```powershell
.\.venv\Scripts\specguard compare examples/retention/before.md examples/retention/after.md --output reports/retention-comparison.html
```

Откройте четыре цитаты и значение 86 400 секунд. Пара согласована. Если удалить RC-2 в отдельной копии, прежнее замечание уйдёт на ручную сверку. Так можно показать жюри цену ошибочного зелёного статуса без выдуманной денежной оценки.

**1 минута — проверка качества.** Откройте metrics из запуска `benchmark.py --suite all`. Единица совпадения — категория и строки размеченного дефекта. Покажите один положительный и один отрицательный пример из массива cases. Облачное сравнение допустимо только для двух завершённых серий на одном корпусе. Для промышленного пилота нужны новые документы и независимый аналитик.

**1 минута — ценность.** Покажите, какое решение должен принять владелец до разработки и какой тест изменится вслед за ним. Предложите пилот с замером времени ручного ревью, времени перепроверки отчёта и доли замечаний, принятых аналитиками. Денежный эффект можно посчитать после получения этих данных.

**Как измерить эффект пилота.** Два аналитика получают сопоставимые документы. Для половины документов первый работает с отчётом, второй вручную, для другой половины порядок меняется. Засеките минуты от открытия ТЗ до согласованного списка вопросов, включая отбраковку ложных сигналов. Третий специалист без указания метода сводит дубли и подтверждает дефекты. Сравните медиану времени и число верно выявленных критичных дефектов на документ. Источник тарифов и стоимость API фиксируются отдельно, если появятся расходы.
